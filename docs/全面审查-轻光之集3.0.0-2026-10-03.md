## P1 优先修复

### F01 阅读页保存后 正文与落笔记忆分裂

**触发**：通过书房的章问题入口或章节阅读页，编辑一章已经采用的正文并保存，然后回落笔或生成下一章。这条阅读页入口也能服务新书，不限于历史旧书。

**实际结果**：阅读页保存只更新章节文件和目录，并清理旧 runtime 状态；新 workflow artifact、manifest、chapter state ref 和 serial ledger 没有同步。隔离样本把“林带着信封离开”改成“林烧掉信封并留在原地”：磁盘正文是新稿，落笔优先加载的 artifact 仍是旧稿。进一步捕获下一章的真实组装请求，里面同时有旧人物状态和新上章结尾，生成路径返回 completed。

**定位**：[ChapterReader.tsx:145](<D:/Grisia Studio/Lightbound/packages/studio/src/pages/ChapterReader.tsx:145>) → [server.ts:3943](<D:/Grisia Studio/Lightbound/packages/studio/src/api/server.ts:3943>) → [edit-controller.ts:331](<D:/Grisia Studio/Lightbound/packages/core/src/interaction/edit-controller.ts:331>)。落笔优先读 artifact：[AuthoringWritePanel.tsx:163](<D:/Grisia Studio/Lightbound/packages/studio/src/components/AuthoringWritePanel.tsx:163>)；新写前检查：[write.ts:212](<D:/Grisia Studio/Lightbound/packages/core/src/authoring/stages/write.ts:212>)。

**已有保护**：旧正文有历史归档，index 被标记为 audit-failed。但新落笔写前检查没有把它转成状态过期约束，不能阻止这次矛盾输入。

**修复与验收**：统一手改正文的提交链。阅读页保存应绑定新 artifact、同步 manifest，并使对应结算失效。可参考现有历史恢复的 `bindRestoredChapterUnlocked` 接线。验收必须跨页面：阅读页保存 → 落笔显示同一稿件 → 下一章请求不再包含旧状态 → 状态整理后使用新记忆。不能只断言 PUT 返回成功。

证据：[reader-repro.mjs](<D:/Grisia Toolbox/codex/tmp/lightbound-stability-20261003/reader-repro.mjs>)。真实文件与实际上下文组装，模型替换为离线 stub；未验证自然语言成稿质量。

### F02 多文件提交中断后缺少恢复 回滚失败还会清掉备份

**触发**：保存候选、自动保存或采用过程中，在旧文件移走、新文件安装完成前进程异常终止；或者安装新文件和恢复备份都失败。

**实际结果**：当前提交先把所有旧目标 rename 到事务目录，再逐个安装新文件。隔离子进程在原 manifest 移走后终止，原路径为 ENOENT，事务目录残留；当前源码没有对应启动恢复扫描。另注入安装与回滚 rename 同时 EPERM，函数报 AggregateError，finally 仍清掉事务目录，目标与该事务备份均消失。EPERM 是模拟异常，不能理解为已观察到用户电脑发生同类权限故障。

**定位**：[atomic-file-set.ts:99](<D:/Grisia Studio/Lightbound/packages/core/src/utils/atomic-file-set.ts:99>)、[atomic-file-set.ts:125](<D:/Grisia Studio/Lightbound/packages/core/src/utils/atomic-file-set.ts:125>)、[atomic-file-set.ts:130](<D:/Grisia Studio/Lightbound/packages/core/src/utils/atomic-file-set.ts:130>)。作者数据调用包括 [chapter-index.ts:196](<D:/Grisia Studio/Lightbound/packages/core/src/authoring/chapter-index.ts:196>) 的正文与索引等提交，以及 [store.ts:308](<D:/Grisia Studio/Lightbound/packages/core/src/authoring/store.ts:308>) 的候选正文和元数据。

**已有保护**：普通异常且回滚成功时能恢复，覆盖正文前通常也存章节历史。历史可降低正文损失，但不能自动重建全部索引和采用关系。不能由本实验推断用户的整本书已经丢失。

**修复与验收**：单文件保留旧目标直到替换；多文件保留足够的事务清单并在启动时恢复。回滚不完整时保留备份，提示恢复位置。逐个 rename 边界终止独立进程，重启后只能得到完整旧状态或完整新状态；双重失败时旧字节仍可恢复。个人本地产品用可恢复文件事务即可。

证据：[atomic-repro.mjs](<D:/Grisia Toolbox/codex/tmp/lightbound-stability-20261003/atomic-repro.mjs>)；主审再次执行得到相同 ENOENT 与回滚备份清空结果。

### F03 织卷重新生成会把旧概要算成本轮完成

**触发**：已经有第 1–8 章概要，再对同一区间按新要求重新生成。第一批 1–4 成功，第二批 5–8 等待或失败。

**实际结果**：第二批尚未返回，run 已显示 completed、8/8。第二批失败后，返回值是 partial，但磁盘 run 仍 completed，missingChapters 为空。候选中前四章是新稿、后四章是旧稿。续跑模型调用 0 次，仍判定完成。前端收到 completed 会停止轮询并解除 busy；没有据此扩大声称已复现并发写坏。

**定位**：[weave.ts:946](<D:/Grisia Studio/Lightbound/packages/core/src/authoring/stages/weave.ts:946>) 将旧概要装进 collected；[weave.ts:1095](<D:/Grisia Studio/Lightbound/packages/core/src/authoring/stages/weave.ts:1095>) 用内容是否非空判断本轮完成；续跑过滤见 [weave.ts:925](<D:/Grisia Studio/Lightbound/packages/core/src/authoring/stages/weave.ts:925>)。

**已有保护**：正式采用稿未被自动覆盖，新生成内容仍是候选，旧稿也保留。缺陷是完成度和恢复语义失真，作者可能误采用混合结果。

**修复与验收**：独立记录本轮 requested/completed 集合，旧稿仅保底。第一批成功时应 running 4/8；第二批失败应 partial、missing=[5,6,7,8]；续跑只做后四章，保留前四章新稿。首次生成、只补空缺、重新生成分别验收。

证据：[weave-regenerate-results.json](<D:/Grisia Toolbox/codex/review-artifacts/lightbound-2026-10-03/weave-regenerate-results.json>)、[复现脚本](<D:/Grisia Toolbox/codex/review-artifacts/lightbound-2026-10-03/weave-regenerate-repro.mjs>)。

## P2 写作过程与长期记忆

### F04 连载账本损坏被按空账本覆盖

[serial-ledger.ts:152](<D:/Grisia Studio/Lightbound/packages/core/src/authoring/serial-ledger.ts:152>) 把不存在、损坏、校验失败、读取失败一律视为 undefined；后续从空账本开始写。隔离样本已有第 1、2 章和早期伏笔，截断 JSON 后重整第 2 章，返回 settled:true，账本从 [1,2] 变成 [2]，早期伏笔消失。

只有正常不存在才应初始化空账本；其他情况保留原字节并明确报错，提供从快照恢复的路径。验收损坏 JSON、读取失败、首章新建三种情况；前两种不能被当前单章数据静默替代。

### F05 状态整理缺少旧伏笔身份 并直接截掉长章尾部

[write.ts:746](<D:/Grisia Studio/Lightbound/packages/core/src/authoring/stages/write.ts:746>) 和 [write.ts:862](<D:/Grisia Studio/Lightbound/packages/core/src/authoring/stages/write.ts:862>) 要模型给出旧伏笔推进／回收 ID，却不提供现有 ID、标签或人物现状；同时只送前 8,000 字符。捕获请求证实：已有不透明伏笔 ID 及标签均不在输入，8,200 字后的结尾标记也不在输入，状态仍可标 settled:true。

这是输入缺口，不是假定每次模型都会回收失败。应加入精简的旧人物/伏笔表，完整处理正文或分段合并，并记录覆盖范围。用埋线→推进→回收三章链，以及 8,500 字末段转折验收同一 ID 与最终人物状态。

F04、F05 证据：[settle-repro.mjs](<D:/Grisia Toolbox/codex/tmp/lightbound-stability-20261003/settle-repro.mjs>)。

### F06 研墨修订和织卷审查取消后仍会提交

UI 有“放弃这次运行／取消”，但 [ground.ts:473](<D:/Grisia Studio/Lightbound/packages/core/src/authoring/stages/ground.ts:473>) 与 [weave.ts:1151](<D:/Grisia Studio/Lightbound/packages/core/src/authoring/stages/weave.ts:1151>) 没有贯通运行取消。离线延迟响应实验中，取消已落盘，模型没有 signal；响应回来后研墨仍替换候选，织卷仍保存报告、标 completed。并非所有阶段的取消都失效，也不会自动采用成果。
