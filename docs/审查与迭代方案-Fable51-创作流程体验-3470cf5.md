## 〇、一段话结论

2.2.x 已把「生成 → 审查 → 按意见修改 → 采用」四阶段骨架、八角色模型、候选/正式稿分离做实，稳定性修了一大轮（2.2.4–2.2.7）。**现在最影响每天使用的不是缺功能，而是三类摩擦：**

1. **新旧两套动线并存**：建书有「聊天确认卡 → `ask_create`」和「右栏整理正典 → 采用」两条路，结果不同；落笔页与书房还露着旧管线的「写下一章 / 改写 / 修订 / 等你过目」，它们**绕过候选与采用直接写正文**（`BookDetail.tsx` L479–565、L605–690；`BookStudy.tsx` L186–200、L330–345）。
2. **长任务同步阻塞、无进度**：问心整理、研墨批量生成、织卷分卷、落笔写章、落笔采用后的状态整理，全部是一次 HTTP 等到底（`authoring-routes.ts` 只有织卷 generate/revise 走 runId）。作者在模态框里盯着「正在生成…」几分钟，无法暂停、看不到进度或流式文字，离开页面结果也不会主动回来。
3. **数据语义不一致**：篇幅默认值有三套（建书提示词 200/3000、轻量建书 36/3000、正典规则「未定用 null」）；`chapterWordCount` 从不以中文明确出现在落笔提示词；织卷每写一卷都要先「采用整份规划」；`thinkingBudget` 与温度在 Claude Opus 5 上实际被忽略但界面不提示。

P0 的动作是：**收口成一条建书动线**、**把落笔页/书房的旧管线入口对四阶段书隐藏**、**四阶段所有生成/修订/采用统一为后台 run + 进度 + 可离开**、**篇幅默认值只保留一处并在织卷前强制确认**、**修好确认卡在重载后仍可点的问题（已随本文修）**。

### 1.2 建书交接（book create handoff）现状

`#/book/new` 同屏两条路：

- **A 路（聊天确认卡）**：`buildBookCreatePrompt`（`agent-system-prompt.ts` L165–177）要求模型凑齐「书名/题材/平台/篇幅」出确认卡，**没说篇幅就填默认 200/3000**（L171、L173）。确认 → `ask_create` → `createAskBookCandidate`：先在 `.inkos/authoring-drafts/ask-create-*` 暂存目录跑 `generateAskCanon`，成功后整目录 `rename` 到 `books/<id>`（`ask-book-create.ts` L100–163），书内只有**未采用**的正典候选；`book:created{canonCandidate:true}` → `bookCreatedRoute` 跳到 `#/book/:id/ask`（`use-session-events.ts` L16–22）。工具回复：「《X》已建书，故事正典已整理为候选。请核对、审查并采用后再进入研墨。」
- **B 路（右栏）**：`AskCanonPanel` 在无书时 `POST /authoring/drafts/ensure` 建草稿根（`.inkos/authoring-drafts/<draftId>`），「整理正典」→ 候选 → 「采用」→ `adoptAskCanon` → `createLightweightBook`，书立即带**已采用**正典，且**篇幅缺省时静默补 36/3000**（`book-create.ts` L128–129）。

两条路都能成书，但一条要作者再审查采用、一条已采用；一条不补篇幅、一条补 36/3000、聊天卡又补 200/3000。而 `CANON_OUTPUT_INSTRUCTIONS` 明确要求「未定篇幅使用 null，不要自行决定」（`stages/ask.ts` L190）。`targetChapters` 直接决定织卷全书规划规模（`weave.ts` `resolveWeaveTargetChapters` L640–650：正典 → book.json → hint → 抛「找不到全书目标章数」）。

### 1.3 Claude 采样 / 输出额度现状

- `omitsClaudeSampling()` 用正则匹配 `claude-opus-4.7/4.8/5`、`claude-sonnet-5`，在 `chatCompletionViaPiAi`、三条自定义传输和 `guardedPiStream` 发包前删除 `temperature/top_p/top_k`。覆盖面完整（含 `onPayload` 钩子链）。
- 输出额度：四阶段 `completeRole` → `chatCompletion(client, model, messages, { temperature, extra })`（`authoring/llm.ts` L15–18），**不传 `maxTokens`**，落到 `client.defaults.maxTokens`：命中模型卡取 `maxOutput`（Opus 5 = 128k；`anthropic.ts` 新增卡、`lookup.ts` 增加 ZenMux 两条核实网关 ID），未知模型取 24576。`assertWithinContextWindow` 用「输入估算 + 预留输出」校验（未知模型上下文按 128k 估）。对 Opus 5 一律预留 128k 输出属于保守但不出错的做法；对经网关转发、实际 `max_tokens` 上限更低的自定义服务，**是否会因 128k 预留被网关拒绝属推测，需实机核对**。
- 输出上限耗尽：`PartialResponseError(reason="output-limit")` 不再盲目重试并给中文提示「模型达到单次输出上限（length）…请检查模型输出额度，或将本次生成拆成更小的任务」（`provider.ts` L551–556、L910–914）。织卷已按 4 章一批拆分（`weave.ts` L869–871、L1166）。
- `thinkingBudget`：角色 schema 有该字段，但 `AuthoringRolesPanel` 不暴露；后端只用来置 `piModel.reasoning` 与 trace header（`provider.ts` L473–477、L1644–1647），**没有把 budget 送进请求体**。温度：面板可填 0–2，对 Claude 5 系列实际被删除，界面无提示。

### 1.4 Studio 面板 / 页面现状

## 二、体验 / 流程痛点（按优先级）

### P0 级（每本新书、每天都会撞到）

**F1. 建书有两条结果不同的路，作者不知道该点哪一个。**
`#/book/new` 左边模型催「出确认卡」，右边有「整理正典」。A 路成书后正典是候选、需再采用；B 路成书即采用。篇幅默认值：A 路 200/3000（提示词硬编码）、B 路 36/3000（`createLightweightBook`）、正典规则 null。后果：作者以为「没填章数就是待定」，织卷却按 200 章或 36 章规划全书；两条路的书 `book.json` 字段也不一致（A 路 `targetChapters` 可能为空，B 路必有值）。

**F2. 落笔页与书房仍露旧管线入口，且这些入口绕过候选 / 采用。**
`/books/:id/rewrite/:n`、`/revise/:n`、`/resync/:n`、`/audit/:n`、`/write-next` 都不检查 `isLightweightAuthoringBook`（`server.ts` 仅 L1859、L3479、L6733 三处检查，全在建书状态与 volume_map 写入），当前章「⋯」菜单的「改写 / 局部修 / 润色 / 重写 / 重构 / 去 AI 味」会直接覆盖 `chapters/*.md`，`manifest.adopted.write` 与文件内容脱节；「等你过目 / 批准 / 回滚」是另一套状态机（`ready-for-review`）。书房主 CTA「落墨 · 写下一章」对四阶段书永远显示「请先写骨架」这类旧世界的原因。

**F3. 长任务一次 HTTP 等到底，作者被锁在模态里。**
落笔写一章、研墨批量生成（N 条串行）、织卷分卷、问心整理、落笔采用后的状态整理，全部同步。`RegenerateDialog` 在 `working` 时禁止关闭；落笔生成没有 running run，服务端崩溃 / 前端刷新后无从得知是否还在跑、也无失败记录；研墨失败条目只有「失败条目：xxx」不给原因（`ground.ts` L220–223 `void error`）。写一章 3000 字在 Opus 5 上常见 1–3 分钟，作者这段时间不能读上一章、不能改设定。

**F4. 织卷「每卷都要先采用整份规划」。**
「生成本卷章概要」按钮要求 `currentId === adoptedId`；核心 `generateWeaveRange` 对四阶段书要求 `manifest.adopted.weave`（`weave.ts` L789–791）。作者流程变成：分卷 → 采用 → 第 1 卷概要 → 采用 → 第 2 卷概要 → 采用……每次采用都会写 `volume_map.md` 并触发下游 watches（「大纲可能需要核对」）。同时整份规划只能在一块 textarea 里手改，几十章概要滚动定位困难。

**F5. 落笔目录看不到「规划了但没写」的章和「有候选未采用」的章。**
目录来自 `/books/:id`（已落盘章节）+ `nextChapter`。作者想跳去第 7 章写候选，必须在「新章」按钮上一路推进；某章生成了候选但没采用，目录里没有任何标记，重开 Studio 容易忘掉。

### P1 级（提升顺畅度与可信度）

**F6. 篇幅 / 字数没有以人话进入落笔提示词。** `serializeCanonBrief` 输出目标章数但**不输出每章字数**（`context.ts` L183–197）；`chapterWordCount` 只藏在正典 YAML 头 `chapterWordCount: 3000`。落笔标题栏只显示当前字数（`AuthoringWritePanel.tsx` L206），无目标对照，也不在审查提示里核对篇幅。

**F7. 研墨条目彼此看不见。** `generateGroundEntries` 每条只给 `serializeCanonBrief(canon)` + 该条旧稿（`ground.ts` L197–203），不带同书其他已生成 / 已采用条目 → 人物条目与势力条目互相打架，要靠审查兜底；而审查（`reviewGroundEntries`）才用 `assembleAuthoringContext`。

**F8. 「创作本章」第一次也弹「保留内容 / 修改重点」对话框。** 首次没有可保留内容，标签不贴切；且这个对话框是所有生成的唯一入口，多一步点击。

**F9. 「比较修改前后」是按行号对齐的朴素 diff。** `diffLines`（`write.ts` L400–414）逐行位置比较，插入一句后全篇标红 / 标绿，几乎不可读。

**F10. 八角色面板「服务连接 / 模型」是自由文本框。** `AuthoringRolesPanel.tsx` L226–263 没有下拉，没法从已配置的服务与模型列表里选；温度对 Claude 5 系列被忽略不提示；`thinkingBudget` 有 schema 无界面、有界面也不会送到请求体。

**F11. 采用后的「下一步」靠 toast，没有明确交接。** 问心采用 → toast「正典已采用」；研墨采用 → toast「已采用 N 项」；织卷采用 → toast「规划已采用」；落笔采用 → toast。都没有「进入研墨 / 去织卷 / 写下一章」按钮，作者要回顶部 chrome 点下一步。

**F12. 文案与状态判定沿用旧模型。** 见 1.4「文案遗留」；`inferGroundDone` 采用 1 条设定即「研墨完成」，书房四步一览会过早打勾。

### P2 级（打磨）
