# 交给 Grokbuild 的开工说明

请在现有 `qingyou0420/Inkborne` 项目中实施四 Agent 小说创作工作台。项目仅供个人在本地使用，沿用现有 Electron、React Studio、Hono 和 InkOS 能力。

这份包是设计交付，不是已实现代码。不要把PDF演示画面中的进度、模型别名和小说数据写死到正式产品里。

## 先读什么

1. `墨生万象-前端页面设计稿.pdf`：12张静态画板，了解视觉、布局和核心操作位置。画板外说明与页码不进入产品。
2. `墨生万象-前端交互规格-Grokbuild交付.md`：行为、状态、保存、版本、范围、八角色配置、窄窗与验收的主要依据。
3. `墨生万象-四Agent协作重构规划.md`：已核实的代码调用链、业务拆分、文件数据来源、六期实施方案和代码落点。
4. `前端设计画板索引.json`：S01-S12页名和注释索引，便于定位画板。

文字规格对实际状态变化的定义优先于PDF中的示意状态。视觉沿用仓库本地字体和主题变量；PDF标题使用了嵌入楷体作近似展示，实际产品使用LXGW WenKai。

## 必须保持的产品意图

- 问心与作者聊天，形成故事正典，采用后轻量建书。建书不包办设定、大纲和审查。
- 研墨根据已采用正典形成适合本书的全部所需设定，支持分项打磨。
- 织卷根据作者要求、正典和设定形成全书大纲、卷纲及每章概要。选择全书时要完成全部目标章数，可分批、暂停和恢复。
- 落笔依据前三步和已采用前文写作，支持手改与局部改写。
- 四个主Agent及其四个审查角色拥有八份独立模型配置；参数、角色说明和实际请求都按角色生效。共享连接可以，改一个角色不能联动其他七个。
- 生成 → 可编辑候选 → 用户主动审查 → 选择意见 → 主Agent按意见修改 → 版本比较 → 用户采用。审查可跳过；没有自动无限审查重写。
- 报告绑定成果版本与审查依据；手改后旧报告明确标记。生成和审查不静默覆盖已采用成果。
- 新稿的摘要/人物状态不能污染正式连载状态；采用与恢复后版本关系明确。正文保存成功和辅助整理失败分别提示。
- 书籍、正文、历史、目录、服务库及现有工具继续可用。避免无必要重写桌面架构或增加商业化管理功能。

## 开始实施

审查基线是 `master` 提交 `4d0c0f5a53e733bace887e4169c15015a21ac482`，桌面版本2.1.9。先查看当前仓库与AGENTS.md，比较基线后续变动，保护已有未提交修改。设计包不是要求重置到旧提交。

按重构规划的M0-M5顺序落地：先统一八角色解析、成果版本和报告存储；再完整实现问心的生成/审查/修改/采用闭环；继续研墨、织卷全章规划、落笔及旧书兼容。先交付能用真实数据完成的一条流程，再复用公共组件扩展其他阶段。

公共组件至少覆盖阶段头部与模型入口、成果版本/保存状态、范围选择、任务进度、审查侧栏、差异比较、采用操作、依据更新提示。组件命名、具体接口路径和内部文件拆分由你结合现有工程决定。

实现中需要真实后端语义支持的部分，不能只改前端标签来替代：八角色实际模型路由、建书拆分、全章概要、版本绑定审查、指定报告修订、采用与状态同步、旧书接入。若本次只安排一个里程碑，明确其完成范围与后续项。

无需额外接入新的通用多Agent框架。项目根目录显式传入；桌面壳决定引擎端口；不要恢复旧Next.js/IndexedDB架构；保留现有许可证与上游署名。

## 怎么验收

以交互规格第17节为功能清单，并运行项目适用的构建、类型检查和关键流程测试。尤其用可区分的八套测试配置核对实际请求，验证失败恢复、旧版报告、部分生成和手改冲突。

在1440×900、1100×900及1024×700核对画板对应布局，检查浅色/暗色、长篇文本、长书名、长模型名、中文输入法和200%缩放。PDF是静态设计依据，不能以页面看起来相似代替行为验证。

每期交付说明实际变更、验证证据、仍未接通的部分与旧书兼容情况。不要宣称尚未测试的流程已经完成。
