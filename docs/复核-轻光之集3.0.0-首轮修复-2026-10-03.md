## P1 F02 恢复旧状态时遗漏本轮新建文件

位置：[atomic-file-set.ts 第 196 行](<D:/Grisia Studio/Lightbound/packages/core/src/utils/atomic-file-set.ts:196>)。

恢复分支只还原有备份的目标，然后删除事务目录、返回 `restored-old`。本轮首次创建的文件没有备份，因此已落盘的新文件不会被撤回。

隔离子进程调用实际 `persistAdoptedChapter` 采用第一章，在正文文件的 rename 完成后直接结束进程，没有经过异常回滚。恢复后：

- `chapters/index.json` 恢复为 `[]`。
- 新正文 `chapters/0001_new.md` 仍存在。
- `resolveChapterFile(bookDir, 1)` 仍能找到这份正文。
- 恢复结果却是 `restored-old`，事务目录已被清理，第二次恢复无事可做。

另一个包含改名章节和旧状态的文件集合实验，恢复后新旧两个章文件并存、状态仍为旧值。这不满足完整旧树或完整新树的验收要求。

本次已生效的部分：仅替换既有文件时，真正结束进程后的恢复通过；安装和回滚同时 EPERM 时，事务目录和旧字节确实保留。

修复边界：事务需记录哪些目标原本不存在。决定回到旧状态时，恢复原文件并撤回本轮新增目标；恢复过程本身也应允许再次执行。针对首章采用和章节改名补真实子进程终止测试。现有 `recovers a complete old tree after a crash mid-install` 测试只是抛一个带 `code: SIGKILL` 的异常，会进入正常 catch 回滚，随后扫描到的事务可以是空集合，不能替代进程中断测试。

证据：[实际章节提交实验](<D:/Grisia Toolbox/codex/tmp/lightbound-recheck-20261003/storage/chapter-results.json>)、[文件集合实验](<D:/Grisia Toolbox/codex/tmp/lightbound-recheck-20261003/storage/results.json>)。复跑脚本分别为同目录 `chapter-recheck.mjs`、`recheck.mjs`，只创建隔离样本。

## P2 回改伏笔起源章后丢失原身份对照

位置：[write.ts 第 747 行](<D:/Grisia Studio/Lightbound/packages/core/src/authoring/stages/write.ts:747>)、[serial-ledger.ts 第 235 行](<D:/Grisia Studio/Lightbound/packages/core/src/authoring/serial-ledger.ts:235>)。

先让同一伏笔在三章经历 open、advance、resolve，再通过实际阅读页 PUT 只修改第一章一句普通文字。保存绑定新 artifact 后，第一章旧 ledger 被版本过滤；重新整理第一章时，原伏笔 ID 已不在请求中，而后两章仍引用旧 ID。

身份对照缺失是已确认事实。隔离响应若为同一伏笔给出新 ID，现有回收记录便匹配不上，已回收伏笔变为 open。没有调用真实模型，不能断言每次都会生成新 ID；但当前流程没有保证稳定身份的依据。

建议把本章旧伏笔 ID 和标签单独作为重整身份对照，避免把旧人物状态重新当作有效事实；或维护稳定身份映射。验收使用不透明 ID，回改无关错字后仍保持已回收，另外验证真正删除伏笔时不会强行保留旧状态。

证据：[记忆实验结果](<D:/Grisia Toolbox/codex/tmp/lightbound-recheck-20261003/memory/results.json>) 中 `F01-F05-hook-identity-after-reader-edit`。F01 原来的“新正文加旧人物状态进入下一章”触发已通过，不能因此忽略这个不同的长期写作场景。
