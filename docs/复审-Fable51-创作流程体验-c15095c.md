## 三、仍会卡住日常写作动线的摩擦

分级：**A 必须返工才能收口** / **B 下一轮（可与 UI 轮并行）** / **C UI 轮** / **D P2**。

### A · 必须返工

**F-1（A）孤儿 `running` 运行记录把面板永久锁死。**
- 现象：落笔「创作本章」跑到一半关掉 Studio（或崩溃、断电）。重开后 `GET /authoring/workspace` 的 `runs[]` 里第一条仍是 `status: "running"`；`AuthoringWritePanel` 的 `lastWriteRun` 效果把它设为 `activeRunId`，`useAuthoringRun` 一直轮询到 `running`，`locked = busy || authoringRun.active` 为真 → 编辑 / 审查 / 采用 / 创作本章全部禁用，状态栏显示「正在写第 N 章 · 已 3h12m」并持续计时。研墨 `blocked`、问心 `locked` 同理；织卷 `running` 为真，只剩一个对死 run 无效的「暂停」。
- 根因：服务端没有为 authoring run 做与聊天任务同类的重启扫尾（`server.ts` 对聊天任务有「任务已中断：Studio 服务在任务运行期间重启」的改写；`authoring-routes.ts` 没有对应逻辑，也没有内存中的活跃 run 登记，`/runs/:id/cancel` 只写 control 文件，死 run 永远不会消费它）。前端四个面板都没有「取消 / 放弃」按钮。
- 为什么是 P0：P0-3 之前是同步 HTTP，进程重启 = 请求失败 = 无残留状态；P0-3 把状态落盘却没配回收，把「偶发失败」升级成「重开后不能写」。写一章常见 1–3 分钟，关窗概率不低。
- 修法（PR-F-a）：`registerAuthoringRoutes` 记 `serverStartedAt`；在 `GET /authoring/runs/:runId` 与 `GET /authoring/workspace` 读取 run 时，凡 `status ∈ {running, pausing}` 且 `updatedAt < serverStartedAt` 的记录改写为 `failed`，`error = "Studio 重启时这次运行已中断，请重新发起。"` 并 `emitAuthoringRun`。同时在 `authoring-routes.ts` 维护一个进程内 `Set<runId>` 的活跃工作表，`/runs/:id/cancel` 对表内 run 写 control，对表外的 `running` run 直接标 `cancelled`。前端问心 / 研墨 / 落笔状态栏在 `active` 时给一个「放弃这次运行」按钮调用 cancel（织卷已有暂停位，加取消）。

**F-2（A，已修）织卷「审查」按钮崩页。**
- `AuthoringWeavePanel.reviewCurrent` 把 `postApi("/authoring/weave/review", …)` 的返回直接 `setReport(next)`；#130 后该路由默认返回 `{ runId, status: "running" }`；`AuthoringReviewDrawer` 顶层计算 `historical = Boolean(report && currentArtifactId && !report.targetRefs.includes(currentArtifactId))` → `targetRefs` 为 `undefined` → TypeError。本地用临时用例复现（`renderToStaticMarkup` 传 `{ runId, status }` 即抛）。四阶段其余调用点都已用 `isBackgroundAuthoringStart` 分流，只有这一处漏了。
- 修法：本文补 `wait: true`（见「五」）。织卷审查因此暂时保持同步（与 #130 之前一致），在 PR-F 里可再按其它面板的模式后台化。

**F-3（A）「采用并建书」之后，聊天会话不跟着书走。**
- `/authoring/ask/adopt` 成书路径只做 `createLightweightBook + bindDraftToBook`，不调用 `migrateBookSession`，也不广播 `book:created`；`use-session-events.ts` 里现成的「把 session 从 null 迁到新书、清 localStorage、跳转」逻辑因此不触发。结果：`onAdopted → nav.toAsk(id)` 落到新书问心页，`ChatPage mode="book"` 找不到 `bookId=id` 的会话 → 聊天区为空；讨论正典的那条会话留在 `bookId=null` 的 `book-create` 列表里。旧 A 路（`ask_create`）是迁移的；P0-1 把 A 路关掉后这个缺口就成了唯一路径的缺口。
- 影响面：模型侧无损（`askAuthorContext` 沿 `manifest.draftId` 读草稿的 `source-conversation.md` 与快照，`authoring-ask-source-persistence.test.ts` 有覆盖）；作者侧「问心 → 研墨」交接时看不到自己刚说过的话，回问心页想继续聊要从头来。第二本书不会误续上一本（`isReusableBookCreateSession` 要求 `messageCount === 0`），这点没问题。
- 修法（PR-F-b）：`ask/adopt` 在 `result.created` 且 `loadDraft(draftId).sessionId` 存在时，调用 `migrateBookSession(root, sessionId, bookId)`（`SessionAlreadyMigratedError` 忽略），再 `deps.broadcast("book:created", { sessionId, bookId, canonCandidate: false })`。`bookCreatedRoute` 会把 `book-create` 页跳到书房，`onAdopted` 会跳到问心，二者取一（建议保留问心，给 `book:created` 加 `stage: "ask"` 或直接让 `bookCreatedRoute` 在 `canonCandidate=false` 时也去 `book-ask`）。`authoring-routes` 需要通过 deps 拿到 `migrateBookSession`（或在 `server.ts` 注册路由处包一层）。补 `use-session-events.test.ts` 与路由测试。

**F-4（A，小）「上一次运行」挑选与「重试」语义不对。**
- `AuthoringWritePanel` 用 `data.runs.find(stage === "write")` 取最新一条写作 run，不看 `scope`（章号）也不看 `operation`；只要它是 `failed` 就在**每一章**的状态栏显示错误 + 「重试」，直到有新的写作 run 覆盖。「重试」在 `operation !== "settle" || !settleArtifactId` 时一律走 `generateChapter(当前章)`：上次失败的是第 5 章审查、现在在第 7 章点重试 → 重新生成第 7 章；采用第 N 章后跳到 N+1，settle 失败 → 面板已重挂载、`settleArtifactId` 为空 → 「重试」变成给 N+1 重新生成。问心「重试」同样对 review / revise 失败一律 `regenerate("")`。
- 修法（PR-F-c）：落笔只认 `run.scope === "chapter:N"` 的 run；重挂载时只自动接管 `running / pausing`（`failed` 仅在本次会话内显示或限定 10 分钟内）；「重试」按 `run.operation` 分派：settle → `/write/settle`（artifactId 取 `run.producedArtifactIds[0]`），review → 重新审查，generate / revise → 重新生成。问心、研墨同法。同时 `producedArtifactIds[0]` 写入 `pendingSavedId` 前也应校验 scope。

**F-5（A，小）`wait=false` 路由在 running 记录落盘前抛错 → 无记录、无提示、无限轮询。**
- `ask/generate|review|revise`、`ground/generate`、`weave/structure|review`、`write/*` 都是先 `const work = fn(...)` 再返回 `{ runId }`，running 记录由核心层在若干 `await`（`askAuthorContext`、`assertAdoptedCanonReady`、`loadArtifact`、`resolve`）之后才写；这段窗口内抛错时 `recordRunFailure` 查不到 run 直接返回，SSE 也不发。前端 `useAuthoringRun` 对 404 只 `setError`，`pollWeaveRun` 在 `catch` 后 `keepPolling` 仍为 true → 每秒一次 404 直到离开页面；三个面板都不渲染 `authoringRun.error`。作者看到的是「点了没反应」。`ground/catalog|review|revise` 与 `weave/generate|revise` 已经在路由层先 `saveRun(running)`，是正确样板。
- 另一个同源边角：`generateGroundEntries` 在 `targets.length === 0` 时写完 `running「没有需要生成的条目」` 后循环不执行，记录永远 running（当前 UI 会在 0 项时禁用入口，仅归档条目 id 传入时可触发）。
- 修法（PR-F-d）：所有 `wait=false` 路由统一在返回前 `saveRun(running)`（用 `emptyRun(stage, operation, roleId)` 小工厂），核心层已有的 `persistRun(running)` 变成幂等覆盖；`generateGroundEntries` 在空 targets 时直接 `completed`。`useAuthoringRun` 连续 N 次 404（如 10 次）后停止轮询并把错误显示到面板状态栏。

**F-8（A，工程）14 例基线即失败、但不在 CI 列表里的测试。**

## 附 · 不收口的判断依据

方案「〇」把 P0 的目标定为「收口成一条建书动线、旧管线入口隐藏、四阶段统一后台 run + 进度 + 可离开、篇幅一处真值、确认卡修复」。前四项里三项已成立；「后台 run + 可离开」在正常路径成立，但「可离开」的另一半——**离开后（包括进程退出）回来能恢复或放弃**——没有，且比 P0-3 之前更差（同步时代无残留）。加上唯一建书路径成书后丢聊天上下文，这两点都落在「每本新书、每天都会撞到」的 P0 口径里。PR-F 五项都是小改（估计 < 300 行含测试），合入并实机走一遍后，创作流程轮即可收口，进入水墨 UI 方案轮。
